# Annotation protocol v1

## Purpose and unit of annotation

“Safe” is an **operational, time- and context-specific research label**, not an intrinsic file property. Metadata alone cannot prove that a file is dispensable. Annotate individual regular files; directory context is evidence, not a label for all descendants. Do not label by bulk extension/path assumptions or by running the model first.

Participants consent to metadata collection and, separately, optional hashing. Do not collect file contents into the dataset. Raw paths, file names and content hashes may expose sensitive information: keep them private, restrict access, use stable user/device pseudonyms and a documented retention/deletion schedule for the research dataset. Participants can exclude private folders; record exclusions and the resulting scope bias. Do not publish private scan databases.

## Operational labels

### SAFE (conditional research label)

All conditions must hold, with evidence recorded:

1. The owner/application documentation explicitly identifies the file as disposable in the observed context.
2. The owning application's supported cleanup semantics or a controlled recreation experiment establishes regeneration without losing user state.
3. No OS protection, protected/application-state location, dependency, active operation or persistent user-state evidence contradicts that assessment.
4. The file is not the sole copy of personal information, credentials, backups, project edits, local-only packages or unsynchronized data.
5. Evidence includes observation date, source, application/version and conditions (for example “application closed and cache rebuilt in a controlled test”). If verification is unavailable, label UNKNOWN.

Examples: an expendable cache artifact generated by a controlled test application whose owner confirms it contains no user state and whose reconstruction is observed in an isolated environment. Do not experiment by deleting files from a participant's live system. Real application cache entries require application-specific evidence; their directory name alone is insufficient.

### IMPORTANT

Any positive preservation evidence is enough:

- Protected Windows/boot/service/runtime component or verified installed application dependency.
- Application configuration/database/persistent volume, credentials, encryption keys or unique application state.
- Owner identifies the file as necessary, irreplaceable, legally required, unbacked-up or intentionally retained.
- Local project modifications, user-authored data, backups needed for recovery, or offline-only dependencies.

Record why and the consequence category (OS/application failure, loss of state, loss of personal data, security/recovery impact). Do not open sensitive content merely to label it; use owner testimony/application metadata as appropriate.

### UNKNOWN

Use whenever evidence is missing, contradictory, unverifiable or context-dependent. Examples: unfamiliar `.dat`, an old download with unknown owner intent, abandoned-looking archives, potentially active temporary files, generic application data and duplicates without confirmation of a dispensable copy. UNKNOWN is not a weak SAFE and is not removed from evaluation.

### Conflict precedence

Protected/dependency/personal-data evidence overrides “looks like a cache.” Missing protection evidence never implies safety. A SAFE label inconsistent with a deterministic protection finding must be audited; it must not lead to relaxing the safety gate. Retain the original annotation and its correction in the audit trail.

## Orthogonal labels

Annotate **category** (OS/application/configuration/cache/temporary/document/installer/archive/log/development/media/unknown) and **review priority** independently of the safety label. These may be additional columns from the same contextual packet, but do not copy model predictions. A large personal archive can be high-priority *review* while still IMPORTANT; cache classification does not imply SAFE. Record category/priority justifications separately if uncertain, and use unknown.

Priority rubric:

- **high:** owner-relevant storage opportunity with enough contextual evidence to warrant prompt review; not permission to delete.
- **medium:** plausible actionable opportunity, nonurgent or smaller scope.
- **low:** minor opportunity or limited practical benefit.
- **retain:** positive preservation evidence, protected component or necessary personal/application state.
- **unknown:** insufficient evidence to prioritize.

The present agreement command measures the safety label. Category/priority agreement should be independently tabulated for the final dataset, not implied by safety agreement.

## Independent annotation procedure

1. Freeze the consenting cohort, observation date, scan metadata and evidence packet. Record file identity/version and scope.
2. Pilot the rubric on an isolated, non-test set. Discuss ambiguities and revise the protocol **before** final annotation; keep protocol versions.
3. Two distinct annotators label the same records independently, without seeing each other's labels or model outputs. Record participant-owner facts in the shared evidence packet, not informal hints given to just one annotator.
4. Both produce one JSONL row per record:

```json
{"record_id":"observation-001","annotator_id":"annotator-A","label":"unknown","evidence":"2026-11-23: owner cannot establish purpose; regeneration not verified"}
```

5. Validate identical record coverage, unique record IDs, valid labels, different annotator identities and nonempty evidence. The tool checks these structural requirements; independence of people must be enforced administratively.
6. Run `disklens annotations first.jsonl second.jsonl`. Report raw agreement and **Cohen's kappa**, total records, class marginals and disagreement counts. Kappa is undefined (`null`) when both annotators use only the same single class. Do not replace it with 1.0.
7. Preserve pre-adjudication labels. Two SAFE votes without valid operational evidence are not automatically valid ground truth; audit evidence independently.
8. A third independent adjudicator reviews disagreements with the owner/context packet and provides a label and justification:

```json
{"record_id":"observation-001","annotator_id":"adjudicator-C","label":"important","evidence":"Owner confirmed this is the sole recovery archive"}
```

9. Unresolved disagreements remain UNKNOWN. Never force a majority SAFE or discard disagreements to inflate precision. Track reason categories and publish aggregate unresolved rates.
10. Merge final labels with the dataset using `annotations ... --dataset raw.jsonl --out labelled.jsonl`, optionally `--adjudications decisions.jsonl`. This preserves both annotations and the resolution. Recheck label-protection conflicts before finalizing the study.

## Duplicate and related-file grouping

Compute explicit SHA-256 hashes under consent before assigning final partitions. Use one common related-group ID for exact copies, near-identical media, different versions of the same download/template, generated siblings, project dependency families and repeated observations/snapshots of the same file or directory family. All related members must belong to one partition. Exact hashes catch equality; they **do not discover all semantic near-duplicates**. Use provenance, application/project/version IDs and manual review; optional perceptual hashing can be added later.

Group across devices before splitting. Because devices/users must also be disjoint, a family shared across cohorts must be retained in only one partition or excluded from the study with a logged reason. Do not give duplicated content different hashes/group IDs just to pass validation. Publish removal counts and methods without exposing raw content hashes.

## Required annotation report (not yet collected)

- Participant/device counts and consenting scope/exclusions.
- Counts by safety/category/priority labels and device; evidence source distribution.
- Number of independently double-annotated records and annotator identities/roles (pseudonyms).
- Pre-adjudication agreement, kappa and class marginals.
- Disagreements, adjudicated decisions, unresolved UNKNOWN and protection-label conflicts.
- Duplicate/near-duplicate grouping/removal counts and grouping limitations.
- Rubric version, timestamps, audit sample findings and dataset hash.

There are currently **no real annotator agreement measurements** in the repository. Synthetic demo labels and programmatic tests cannot substitute for this report.
